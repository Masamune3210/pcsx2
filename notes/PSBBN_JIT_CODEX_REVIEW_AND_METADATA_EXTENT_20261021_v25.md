## Findings

1. **Codex's compile-time sizing fix is correct.** `MemoryTypes.h` explicitly declares `Ps2MemSize::ExposedRam` as an external runtime `u32`, whereas `Ps2MemSize::TotalRam` is a `static constexpr u32` equal to 128 MiB. A non-type template argument requires the latter. `EERecCompiledPhysicalPages<TotalRam>` occupies 4096 bytes. The filter's runtime high-water/physical bounds still prevent treating beyond-exposed-RAM pages as ordinary compiled code. This correction has NOT been compiled here.
2. **The D-only fast path is defensible, but needs real integration tests.** `HasSameBacking` compares PFN and scratchpad kind, deliberately not EntryLo.D; both COP0 mapping-diff passes keep existing host and JIT aliases when only D changes, and the active map is swapped afterward. `memSetPageAddr`, `recMapTLBPage` and the host pointer do not encode D. `recCheckTLBStore` consults current D on fine-mode store opcodes, and the interpreter checks D before stores. This can eliminate unnecessary code invalidation on COW/dirty transitions without relaxing architecturally read-only pages. However, the new tests only test the pure predicate/map swap, **not actual COP0 synchronization or generated JIT store behavior**. Keep the change experimental pending both D transition directions, COW and native-game tests. Count `permissionOnlyUpdates` before predicting performance gains.
3. **Found and fixed a filter false negative in the inherited code.** `BASEBLOCKEX::startpc` is keyed to the physical start and `BASEBLOCKEX::size` extends contiguously by guest instruction count. The bitmap initially marked the actual `HWADDR` of each virtual source page, which may be noncontiguous across a guest 4 KiB boundary. For example: guest branch at offset `0xffc` starts physical `0x1ffc`, next page maps to physical `0x6000`, and the guest block spans 12 bytes. Actual source PFNs are `0x1000` and `0x6000`, but the block metadata overlaps physical `0x2000`. Before this fix, the bitmap could report `MayContainCode(0x2000,1)==false` and skip `EERecClearPhysicalBlocks`, which would otherwise find the overlapping metadata. This creates a false negative in a correctness-critical invalidation filter.
4. **Committed conservative safety correction.** `EERecCompiledPhysicalPages::MarkMetadataExtent(physicalStart,byteCount)` marks every physical 4 KiB page in the contiguous `BaseBlocks` extent, using a 64-bit end calculation and the bitmap's RAM limit. `recRecompile` calls it after the block's size is established, **in addition to** marking the actual guest-TLB-translated source PFNs. The existing early start-page mark remains. One new regression test demonstrates the original missing bit and verifies it is now marked. This is deliberately conservative and may reduce how many non-code pages get skipped, but cannot suppress a required invalidation.
5. **Larger pre-existing architectural limitation remains:** A block spanning noncontiguous guest physical pages is still represented by `BaseBlocks` as a single contiguous physical extent. Marking both the actual PFNs and the metadata extent repairs this filter's negative-test guarantee; it does **not** make `EERecClearPhysicalBlocks` inherently aware that code in a physically different second PFN belongs to the block. Invalidation of the *actual second PFN* can therefore miss a block that began on another PFN. Correct options include splitting blocks on guest TLB physical discontinuities, interpreting the rare boundary branch, or explicit per-block physical-page dependencies. Do not remove mapping-related invalidations or retain more compiled code until this is resolved. A review-only finding, no speculative complex control-flow alteration committed.
6. **Existing 64 MiB JIT arena churn is not solved by either new Codex commit.** D-only update optimization and bitmap filtering can save some invalidation work, but the arena is bump-allocated, and invalidated host bytes are not reclaimed. Existing measured v22 snapshots still represent the last confirmed performance evidence. No FPS increase was demonstrated.
