## Crash facts from VS debugger (user-supplied)
- Unhandled host `C0000005`, read address 0, in `pcsx2-qtx64-avx2.exe!recRecompile(startpc)` at `pcsx2/x86/ix86-32/iR5900.cpp:2743`.
- `startpc = 263667688 = 0x0FB73FE8`
- `s_nEndBlock = i = 263667716 = 0x0FB74004`
- The crash dereference is `cpuRegs.code = *(int*)PSM(HWADDR(i - 4));`; initial `i-4 = 0x0FB74000`, the **first word on the next 4 KiB guest page**.
- `cpuRegs.code = 4194312 = 0x00400008`, decoding as MIPS `JR $v0`, strongly indicating a `JR` instruction at `0x0FB73FFC` followed by an unmapped cross-page delay slot at `0x0FB74000`. Since this value was captured before the crash while scanning/analysing the block, it is not independent proof of actual bytes at `0x0FB73FFC`; the new compiler guard reads and checks the branch opcode directly.
- `PSM(x)` expands to `vtlb_GetPhyPtr((x)&0x1fffffff)`. `vtlb_GetPhyPtr` returns null on an inaccessible/non-RAM physical page. Thus this is an *ordinary host null dereference in compiler-time instruction analysis*, not the expected fastmem SEH mapping mechanism.

## Cause in compiler
`recRecompile` ordinarily cuts compiled blocks at 4 KiB page boundaries. However, for `JR/JALR`, unconditional jumps, and several conditional branches, the forward scan deliberately sets `s_nEndBlock = branchPC+8` so the branch and its delay slot are in one block, then jumps directly to `StartRecomp`. A branch at page offset `0xFFC` therefore extends into a potentially unmapped next page. Backward opcode analysis unconditionally dereferences that delay slot and host-crashes. An early null guard that simply substitutes NOP would be architecturally wrong, especially for branch-likely annulment and `Cause.BD/EPC`.

## Source repair (rare interpreted branch, normal JIT unchanged)
- In `iR5900.cpp::recRecompile`, after determining end-of-block but before any backward opcode walk, detect a branch ending at page boundary with an unavailable delay slot: `(end & 0xFFF) == 4`, `branchPC = end-8`, `delayPC=end-4`, `(branchPC & 0xFFF)==0xFFC`, `PSM(HWADDR(delayPC))==nullptr`, and branch opcode really has `IS_BRANCH`.
- Trim `s_nEndBlock` from `branchPC+8` to `branchPC+4`, excluding the invalid delay slot from all JIT compile-time analysis. Compile instructions before the branch normally. When the last branch opcode is reached in code generation, flush its JIT GPR/FPR state and call a new interpreter single-branch helper; stop the block with a normal branch event check.
- In `Interpreter.cpp`, `EEInterpretCrossPageBranchFromJIT(branchPC)` runs `execI()` **once**, including any actual delay-slot instruction via the interpreter's own branch implementation. It temporarily sets `Cpu = &intCpu` so a missing delay-slot translation uses its existing TLB exception and `CancelInstruction` path. A bounded `fastjmp_set` scope catches the interpreter's cancel/exit; `intCancelInstruction()` returns a distinct value for this fallback rather than restarting at the exception vector as a second instruction. The helper restores `Cpu=recCpu` and clears its temporary interpreter state before returning to the JIT dispatcher.
- Since the full branch is interpreted **at guest runtime**, not while the JIT is compiling, exceptions from previous instructions still occur first, the branch-likely nullification is honored, `JAL/JALR` link effects use existing interpreter semantics, and guest `TLBL/EPC/BD` are generated by the original fetch path. No PSBBN-specific address constants or forced TLB mappings. The newly added diagnostic is capped at 32 lines (`EE JIT cross-page delay-slot interpreter fallback`).
- Source audit also uncovered pre-existing `Interpreter.cpp::COP0_AdvanceRandom()` decrementing Random once *per interpreted instruction*. The earlier cycle-derived `UpdateTLBRandom()` introduced for JIT TLBWR must not overwrite that already-accurate interpreter state; updated it to be a no-op when `Cpu == &intCpu`. This preserves ordinary PS2 interpreter behavior.
